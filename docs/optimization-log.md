# 优化实录：AI 简历—岗位匹配助手 V1 → V4

本文记录本仓库从初版（V1）到 V4 的优化过程：每一级都按「现象 → 原因分析 → 改法 → 实测结果」写，
所有数字都能用仓库内命令复跑（命令见文末）。**不是结果汇总表，而是决策记录**。

> **离线数字 ≠ 真实模型指标**
>
> 本文所有数字都来自离线模式：确定性规则引擎，不调用大模型，不需要 API Key。
> 它证明的是「评分逻辑没有明显离谱、改动方向有效」，**不能当作真实大模型的抽取/评分效果**。
> 配好 `.env` 后跑同一套命令，得到的才是真实模型指标（见 [README](../README.md) 第 2 节）。
> 报告与评测输出里都会显式标注 `mode`，引用数字时请带上模式与样本量。

## 1. 基线画像（V1）

- 三维评分：硬性要求 60% + 技能覆盖 25% + 经历相关度 15%，权重是经验值（拍脑袋定的）。
- 基线测试：45 个 unittest 全绿；评测 MAE = **6.5 分**（10 组人工标注，见 `eval/labels.csv`）。
- 关键观察：系统分普遍比人工分**低 5-8 分**，是系统性偏差，不是随机误差 —— 说明不是"某几组抽风"，
  而是权重/缩放系数的整体标定有问题。

## 2. V1 → V2：技能别名归一

**现象**：`SKILL_ALIASES`（k8s→kubernetes、大模型→llm、数据清洗→etl 等）明明已经定义在 `app/config.py`，
但 `skill_coverage` 里做集合差集时**没调用它** —— JD 技能和简历技能都还是原始小写值。

**原因分析**：别名归一在 `jd_parser.normalize_skills` 里只对「词表抽出来的技能」用了一次，但
`skill_coverage` 拿到的技能可能来自**大模型输出**（LLM 模式），模型可能输出缩写「k8s」而词表是
「kubernetes」，两个集合做差集就误判成「缺失」。归一的位置放错了 —— 应该在**评分这一层**（比较前）做，
而不是解析层。

**改法**：在 `app/scoring.py` 的 `skill_coverage` 里新增 `_normalize_skill`，对 JD 技能和简历技能**都**
过一遍 `SKILL_ALIASES`，再做交并差。

**代码位置**：`app/config.py`（`SKILL_ALIASES`）、`app/scoring.py`（`_normalize_skill` + `skill_coverage`）。

**实测结果**：补了单测 `test_skill_alias_normalized`（JD 写 kubernetes/llm、简历写 k8s/大模型，覆盖率应为 100%）。
离线词表本身输出标准名，此改动主要保护 LLM 路径，**离线数字不变**（如实记录，不把没变化的数字算成收益）。

**面试一句话**：技能归一要做在「比较之前」而不是「解析之后」—— 因为技能可能来自大模型，模型输出缩写会漏判；
我把归一挪到评分层，保证不管技能从哪来都落在同一套标准名上。

## 3. V2 → V3：权重留一交叉验证校准

**现象**：初版权重 60/25/15 是经验值，系统分普遍比人工分低 5-8 分，MAE 6.5。

**原因分析**：三个维度的权重、以及经历相关度的缩放系数（Jaccard 天然偏小，初版 ×3）都没有用数据标定。
与其手调，不如把「调权重」变成一个可复现的实验。

**改法**：新增 `eval/calibrate_weights.py`：

- 网格搜索权重组合（must ∈ {0.50~0.70}、skill ∈ {0.20~0.30}、exp ∈ {0.10~0.25}，sum=1）
  与缩放系数（2.0~4.0）；
- 用**留一交叉验证（LOOCV）**估计每个组合的真实 MAE，而不是全量 MAE（全量 MAE 会过拟合这 10 组标注）。

**代码位置**：`eval/calibrate_weights.py`（新增）、`app/config.py`（`WEIGHTS`、`EXP_RELEVANCE_SCALE` 更新）。

**实测结果**：

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 权重 | must 60% / skill 25% / exp 15% | must 65% / skill 25% / exp 10% |
| 经历相关度缩放系数 | 3.0 | 4.0 |
| MAE | 6.5 | **4.4** |
| Spearman 秩相关 | — | **0.979** |
| 分档准确率（高/中/低） | — | **100%（10/10）** |

最优组合 `must=0.65, skill=0.25, exp=0.10, scale=4.0`，完整搜索表见
[`eval/weight_calibration.md`](../eval/weight_calibration.md)。

**踩坑（重要）**：10 组样本太小，这个最优组合只能当**方向性结论** —— 「硬性要求权重应更高、
经历相关度权重应更低」。不能宣称这是「全局最优」，样本量不够。方向本身符合直觉
（硬性要求不过关，简历再漂亮也白搭）。

**面试一句话**：我把权重从「拍脑袋」改成「标出来的」—— 在 10 组人工标注上用留一交叉验证网格搜索，
MAE 从 6.5 降到 4.4；同时我诚实标注了样本量小的局限，结论是方向性的。

## 4. V3 → V4：建议优先级分级 + 评测指标升级

**现象**：改写建议是平铺的 3-5 条，用户不知道先改哪条；评测只有 MAE，看不出「排序对不对」。

**原因分析**：建议有轻重缓急 —— 缺失技能/未命中硬性要求直接决定能不能过初筛，量化成果不足只是
「锦上添花」，平铺的列表浪费用户的注意力。评测方面，招聘场景「谁该排前面」比「分数差多少」更有意义，
MAE 只看数值差，看不出排序一致性。

**改法**：

- `app/advisor.py` 的 `_rule_advices` 给每条建议加 `priority` 字段（urgent / important / suggest），
  LLM 建议在 `_clean_advices` 里按 `where` 兜底映射优先级；
- `app/report.py` 渲染优先级标签（【高优·先改】/【重要】/【可选】）；
- `eval/run_eval.py` 新增 **Spearman 秩相关**（排序一致性）和**分档准确率**
  （高 ≥70 / 中 40-69 / 低 <40 三档，同档算对）。

**代码位置**：`app/advisor.py`（priority）、`app/report.py`（标签渲染）、`eval/run_eval.py`（Spearman + 分档）。

**实测结果**：Spearman = 0.979（排序几乎完美一致），分档准确率 = 100%（10/10 全对）。
单测从 45 涨到 **46**（新增别名归一用例等）。

**面试一句话**：评测除了 MAE 我加了 Spearman 和分档准确率，因为招聘场景「谁该排前面」比
「分数差多少」更重要；建议也分了优先级，让用户先改决定过不过初筛的部分。

## 6. 取数口径（诚实约定）

| 指标 | 数字 | 口径与前提 |
| --- | --- | --- |
| MAE | 6.5 → 4.4 | 离线规则引擎，10 组自标注（2 份 JD × 5 份简历） |
| Spearman | 0.979 | 同上 |
| 分档准确率 | 100%（10/10） | 同上 |

**简历/介绍里怎么写这些数字（诚实版）**：

- ✅ 「用留一交叉验证校准评分权重，与人工标注的 MAE 从 6.5 降到 4.4，Spearman 0.979」
- ✅ 「自建 10 组人工标注评测集，补 Spearman 秩相关与分档准确率，分档一致率 100%」
- ❌ 不要写「准确率 100%」这种省略「分档/样本量/离线模式」的说法；
- ❌ 不要写没有标注模式与样本量的数字（离线数字不能冒充真实模型指标）。

> 人工分由我们自己逐条对照 JD 要求给出，**不是行业金标**；样本量 10 组，只用于发现明显偏差。
